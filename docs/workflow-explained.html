LATENT_V2 · quant/data walkthrough

How the workflow works

This guide explains what the repository does from a quantitative and data perspective: what is observed, how it is transformed, which statistical questions are answered, and how factor exposures eventually become benchmark, risk, and trade-proposal inputs.

Module walkthrough Architecture map Detailed math Results page
First distinction: this is not one single model. It is a chain of research models and portfolio tools. The research track explains returns and tests factor quality. The benchmarking track uses selected outputs to compare a portfolio with a policy benchmark. The real-holdings optimizer then converts that comparison into constrained trade proposals.

1. The complete data flow

2. What enters the system?

Fama–French 5 factors

Mkt-RF, SMB, HML, RMW, and CMA are investable-style return streams: market excess return, size, value, profitability, and investment. RF is the risk-free rate and is used to convert asset returns into excess returns; it is not treated as a risky factor.

Macro indicators from FRED

Growth, inflation, yields, monetary policy, currency, credit/risk appetite, and commodities. Daily/weekly series are reduced to the last available observation in each month. The workable panel begins in January 2006 and forward-fills selected macro columns after that point.

Yahoo Finance prices

ETF and holding prices use adjusted monthly closes, so splits and distributions are included. Returns are first stored as percentages (for example, 2.0 means 2%), then converted to decimals (0.02) inside regression and portfolio calculations.

Brokerage workbook

The real track reads account, ticker, market value, cost basis, and aggregated short-/long-term gains. Account tax status is inferred from sheet name. This is the only input that contains household-specific holdings and tax data.

3. Building the macro factors

3.1 Transforming raw macro series

Index and price-like series are converted to month-over-month percentage changes because PCA on trending levels would mostly discover shared time trends. Yields, spreads, rates, VIX, and already-growth-rate series remain in levels. Each category is then standardized to mean zero and unit variance.

3.2 Category-level PCA

Rather than run one PCA across all macro columns, the workflow runs one PCA inside each economic category. The first principal component is retained as that category's factor. PCA chooses the linear combination that explains the greatest standardized variance within the group.

MacroFactor_category,t = PC1(standardized transformed series in category)

The result is nine unitless macro factors. Their sign is mathematical, not intrinsically economic: multiplying a PCA factor and all its loadings by -1 produces the same model fit. Interpret the sign using the loadings printed by quant_model_macro_1.py.

4. The statistical models

VARX: macro conditions and FF returns

quant_model_macro_2.py models each FF factor using lagged values of all five FF factors plus contemporaneous macro PCA factors. The lag order is selected by AIC, with a six-month search cap. Univariate regressions provide a deliberately simple comparison: a relationship that disappears in the VAR may have been correlation with another macro factor.

FF5 asset regressions

For each ETF or holding, the dependent variable is excess return. The multivariate regression estimates the asset's conditional exposure to all five FF factors at once. Univariate regressions show how much a factor's apparent relationship changes when the other factors are omitted.

Full 14-factor regressions

The five FF factors and nine macro factors are used together. The coefficient is an exposure estimate; the intercept is alpha under the model; R² is in-sample explained-return variance, not a forecast guarantee. Assets with fewer than 40 aligned monthly observations are skipped in this expanded model.

HAC / Newey–West inference

Monthly returns can have autocorrelation and changing variance. HAC changes the standard errors and therefore t-statistics, without changing the OLS coefficient itself. The workflow compares plain OLS and HAC t-statistics to see whether inference is sensitive to serial correlation.

ExcessReturn_i,t = α_i + β_i' Factor_t + ε_i,t
t-statistic = estimated coefficient / estimated standard error

5. Diagnostics: what can and cannot be trusted?

DiagnosticQuestionMeaning of a good result
VIFAre the 14 regressors redundant?Low VIF means coefficient instability is less likely to be caused by multicollinearity. The committed result's maximum is about 2.17.
HAC vs OLSDoes serial correlation change significance?Few significance flips imply autocorrelation is not the main reason a factor looks weak.
Empirical-Bayes τ̂Is beta dispersion across assets larger than estimation noise?τ̂ near zero means observed cross-sectional beta differences are not distinguishable from noise in this sample.
R² / residualsHow much return variation is left unexplained?Low residual risk is useful for a factor-only risk model; low R² warns that factor TE may understate actual portfolio risk.

Important: statistical significance is not economic investability.

A macro PCA score is an explanatory state variable, not a security that can automatically be bought. This is why the benchmark uses only the five FF return streams even though the 14-factor model is useful for understanding asset returns.

6. Constructing the policy benchmark

construct_benchmark_mvo.py uses annualized sample means and covariance of the FF5 returns. It maximizes estimated excess Sharpe ratio subject to long-only weights, a 60–70% market-factor band, and a 5% minimum weight for every non-market factor.

maximize (w'μ) / sqrt(w'Σw)
subject to: Σw = 1; w_i ≥ 0.05 for non-market factors; 0.60 ≤ w_Mkt-RF ≤ 0.70

Here w is a five-element allocation over [Mkt-RF, SMB, HML, RMW, CMA], μ = 12 × mean(monthly factor returns), and Σ = 12 × cov(monthly factor returns). The factor returns are already excess-of-RF streams, so the objective uses w'μ directly. SLSQP solves the constrained nonlinear max-Sharpe problem. The resulting vector is then treated as buy-and-hold: each sleeve compounds independently and effective weights drift. This is different from rebalancing back to the target every month.

N_i,t = w_i × Π_(s≤t)(1 + F_i,s)
q_i,t = N_i,t / Σ_j N_j,t
R_benchmark,t = RF_t + Σ_i q_i,t−1 F_i,t

The benchmark wealth curve is built from that return equation, with the initial month handled using the target weights. Its monthly return series, rather than a constant-weight rebalanced approximation, is used downstream for realized tracking-error and CVaR scenarios. The saved outputs are benchmark_mvo_weights.csv (the fixed target), benchmark_wealth_curve.csv (wealth and returns), and benchmark_effective_weights.csv (the drifting sleeve mix).

Modeling judgment: unconstrained mean-variance optimization is highly sensitive to noisy sample means. The non-market floor is an intentional policy constraint, not a claim that all five factors have statistically positive expected returns.
Benchmark distinction: the factor benchmark allocation is itself optimized from historical FF5 returns and covariance. This differs from the SAA benchmark below, whose allocation is imported directly from the Excel policy-target column. In both cases, benchmark construction comes before household trade optimization.

7.1 How the SAA trade proposal is created

The SAA path minimizes squared covariance-based active TE plus the same L1 turnover regularizer used by the factor/CVaR optimizer. It starts from current household weights, keeps Joint and IRA positions as separate decision variables, and does not introduce new tickers.

minimize_x (Mx − τ)'Ω(Mx − τ) + λ Σ_i |x_i − x0_i|
subject to: Σ_i x_i = 1; x_i ≥ 0; Σ_(i∈ticker t) x_i ≥ 0.3%
Σ_(i taxable) max(x0_i − x_i, 0) × tax_rate_i ≤ 2%

The absolute-value turnover term and taxable sale term are represented with the optimizer's constrained formulation; the resulting account-level weights are converted into trade_proposals_pathSAA.csv. This is a trade proposal that moves toward the SAA policy benchmark, not a claim that the current household already has the benchmark's sleeve exposures.

In short: factor benchmark = optimize the benchmark, then optimize household deviations from it; SAA benchmark = read the benchmark from Excel, then optimize household deviations from it.

8. From holdings to tracking error

7.1 Estimate each holding's exposure

Each ticker is regressed separately on FF5. The portfolio beta is the market-value-weighted sum of ticker betas. The benchmark beta is known directly from its target weights, so it does not need to be estimated.

β_portfolio = Σ_t w_t β_t
Δβ = β_portfolio − β_benchmark

7.2 Ex-ante and ex-post TE

Ex-ante TE prices the active factor exposure using the annualized FF5 covariance matrix. Ex-post TE compares realized portfolio and benchmark return histories over their common overlap.

TE_ex-ante = sqrt(Δβ' Σ Δβ)
TE_ex-post = std(monthly portfolio return − monthly benchmark return) × sqrt(12)

The first is a systematic-factor forecast; the second includes idiosyncratic shocks, timing, data alignment, and anything else the factor model misses. A large gap is therefore diagnostic, not automatically a bug.

9. Real-household optimization

The production track ingests the workbook, downloads monthly prices, estimates ticker betas, and solves for new account-level weights. It does not introduce new tickers: it reweights currently held positions, keeping taxable and IRA rows separate because the same sale has different tax consequences.

Objective

Minimize factor-based active TE squared plus an L1 turnover regularizer. The L1 term discourages cosmetic trades and corner solutions.

Active CVaR

Build overlapping 12-month scenarios from common ticker history. Computed and reported for every path as context — it is not a constraint on any currently-solved path (Path C, Path D, or the SAA path).

Tax budget

Only taxable-account sales consume the 2% household tax budget, with MSTR's own realized tax excluded from that budget entirely for all three paths (a separate taxable strategy is assumed to handle it). Aggregated ST/LT gains are prorated by the fraction sold and taxed at configured assumed rates.

Allocation floor

Every currently held ticker retains at least the configured minimum household allocation, except tickers in NO_ADD_TICKERS (see next card). This is a structural mandate, not a statistical conclusion.

No-add tickers

SHV may be trimmed or sold but never bought further, in every path in both optimizer scripts. Its current weight (0.295%) sits just under the allocation floor, so it is exempted from that floor rather than made infeasible by it.

minimize Δβ'ΣΔβ + λ Σ_i |x_i − x0_i|
subject to: sum(x)=1; TaxCost_ex-MSTR ≤ 2%; ticker floors; SHV ≤ current weight

The absolute values and sale amounts are represented with slack variables, allowing the problem to be handled as a constrained smooth optimization. There is no CVaR constraint in the currently-solved paths, so there is no joint-infeasibility case to relax — each of Path C and Path D is solved directly, differing only in how much of the MSTR position may be sold this year.

10. Full mathematical specification of every optimizer

This section gives the exact, solver-level formulation for each of the three optimizations that feed rebalance_dashboard.html — decision variables, objective, every constraint (including the slack-variable linearizations SLSQP actually sees), and the numeric constants used. Sections 6–9 above give the intuition; this is the precise spec.

10.1 Benchmark construction — construct_benchmark_mvo.py

One-time, non-rebalanced max-Sharpe allocation over the 5 Fama-French factor streams.

variables: w ∈ R^5 (order: Mkt-RF, SMB, HML, RMW, CMA)
maximize: (w'μ) / sqrt(w'Σw)
subject to: Σ_i w_i = 1
0.60 ≤ w_Mkt-RF ≤ 0.70
0.05 ≤ w_i ≤ 1 for i ∈ {SMB, HML, RMW, CMA}

μ = 12 × mean(monthly FF5 returns), Σ = 12 × cov(monthly FF5 returns), full sample, unshrunk. Solved with SLSQP (maxiter=1000, ftol=1e-12). The resulting w is then compounded buy-and-hold (never rebalanced):

N_i,t = w_i · Π_(s≤t) (1 + F_i,s) (per-factor notional)
q_i,t = N_i,t / Σ_j N_j,t (drifting effective weight)
R_benchmark,t = RF_t + Σ_i q_i,t−1 · F_i,t

10.2 Real-household tax optimizer — optimize_tax_cvar_mvo.py

One (ticker, account) row per currently-held position, n rows total. The decision vector is five blocks, always allocated in full regardless of which constraints are switched on for a given solve. Only Path C and Path D are solved from this script now, and both run with the CVaR-floor constraint switched OFF (enforce_cvar=False) — the ζ/u CVaR slack blocks below are still allocated (the decision-vector layout is unconditional, see solve()'s docstring) and CVaR is still computed from them for reporting, it just isn't constrained.

v = [ x (n), ζ (1), u (S), sell (n_Joint), turn (n) ]
BlockMeaningBounds
x_iweight of row i, fraction of total household value[0, 1] (or [x0_i(1−cap), 1] under a MSTR sale cap)
ζCVaR auxiliary variable (≈ estimated VaR cutoff)unbounded
u_sCVaR tail slack, one per scenario s = 1…S[0, ∞)
sell_jsale-fraction slack, one per taxable (Joint) row[0, 1]
turn_iturnover slack, one per row[0, 1]
objective(v) = Δβ(x)'Σ Δβ(x) + λ · Σ_i turn_i (both Path C and Path D)
Δβ(x) = Σ_i x_i β_ticker(i) − β_benchmark (n×5 beta matrix, aggregated across both accounts)

Constraints, in the exact linear/quadratic form the solver sees:

(1) budget: Σ_i x_i = 1
(2) CVaR slack: u_s ≥ Loss_s(x) − ζ, u_s ≥ 0, for every scenario s [computed always, informational]
Loss_s(x) = BenchAnnual_s − Σ_i x_i · A_i,s
(3) CVaR floor: ζ + [1 / (α·S)] · Σ_s u_s ≤ −CVAR_FLOOR [OFF for Path C/D — enforce_cvar=False]
(4) tax slack: sell_j ≥ x0_j − x_j, sell_j ≥ 0, for j ∈ Joint rows
(5) tax budget: Σ_j sell_j · taxRate_j,budget ≤ TAX_BUDGET (0.02, MSTR's rate zeroed in taxRate_j,budget)
(6) turnover: turn_i ≥ x_i − x0_i and turn_i ≥ x0_i − x_i (⇒ turn_i = |x_i − x0_i| at the optimum)
(7) ticker floor: Σ_(i: ticker(i)=t) x_i ≥ MIN_TICKER_WEIGHT, for t ∉ NO_ADD_TICKERS (always on)
(8) no-add bound: x_i ≤ x0_i, for every row where ticker(i) ∈ NO_ADD_TICKERS (bound, not a constraint fn)

Constraint (2) still builds the CVaR slack every solve — the decision-vector layout is unconditional — and the resulting CVaR value is reported in path_metrics.json for every path, but constraint (3), the actual floor, is switched off for both Path C and Path D (enforce_cvar=False). It uses S overlapping 12-month scenarios built from common ticker history: A_i,s = ticker i's summed monthly return over scenario window s, BenchAnnual_s = the benchmark's summed monthly return over the same window. taxRate_j = (LT_Gain_j·TAX_LT + ST_Gain_j·TAX_ST) / MarketValue_j, computed once per Joint-account ticker from the workbook's aggregated (not per-lot) gain figures; taxRate_j,budget is that same vector with MSTR's entry zeroed out (exclude_from_tax_budget={"MSTR"}), so MSTR's sale is free from constraint (5)'s point of view while its true tax cost is still reported in the trade table via the unmodified taxRate_j.

MSTR's row is also bound-restricted: x_MSTR ≥ x0_MSTR · (1 − sell_cap), with sell_cap = 70% for Path C and 30% for Path D — both raised from this optimization's earlier 30%/10% caps, so both paths now permit selling a much larger share of the current MSTR position in a single year.

SHV may be trimmed or sold, but never bought further, in any path. NO_ADD_TICKERS = {"SHV"} caps that row's upper bound at its current weight (constraint (8) above) instead of the usual [0, 1]. SHV's current combined weight is 0.295% — just under MIN_TICKER_WEIGHT (0.3%) — so it is also excluded from constraint (7)'s floor entirely: requiring both "no more than its current weight" and "at least 0.3%" on the same ticker would make the problem infeasible, and the no-add mandate is the deliberate one here. In practice SHV simply holds at its current weight (0.295%) in every path this run — there is no tax or CVaR reason to sell it, only a bound against adding to it.

Solved with SLSQP (analytic Jacobians for every constraint, maxiter=2000, ftol=1e-12). Both Path C and Path D are solved directly through the same solve() function with enforce_cvar=False, enforce_tax_budget=True, exclude_from_tax_budget={"MSTR"}, and a max_sell_frac entry for MSTR — there is no joint-CVaR-and-tax problem attempted first and no relaxation fallback (the earlier "Joint / Path A / Path B" design has been retired from this script entirely; solve() still supports a CVaR-floor constraint and a tax-cost-minimizing objective as general machinery, simply unused by anything currently invoked).

10.3 SAA optimizer — optimize_saa_mvo.py

Reweights the same (ticker, account) rows to track the workbook's sleeve-level policy target instead of the FF5 benchmark. No CVaR constraint — this path only minimizes sleeve-covariance active TE subject to its own tax budget, its own MSTR carve-out/sale-cap, and the ticker floor. This path runs its own, independently tracked 2% tax budget (numerically the same as Path C/D's 2%, but a separate constant, SAA_TAX_BUDGET, not a shared one) and its own MSTR-specific treatment.

variables: x ∈ R^n (row weights, reused from the same holdings table)
minimize: (Mx − τ)'Ω(Mx − τ) + λ · Σ_i |x_i − x0_i|
subject to: Σ_i x_i = 1
x_i ∈ [0, 1] for i not MSTR and not in NO_ADD_TICKERS
x_MSTR ∈ [x0_MSTR · (1 − 0.50), 1] MSTR sale capped at 50% of its current position
x_i ∈ [0, x0_i] for ticker(i) ∈ NO_ADD_TICKERS (SHV): no buys
Σ_j max(x0_j − x_j, 0) · taxable_j · taxRate_j,budget ≤ SAA_TAX_BUDGET (0.02)
Σ_(i: ticker(i)=t) x_i ≥ MIN_TICKER_WEIGHT (0.003), for t ∉ NO_ADD_TICKERS

M is the fixed n_sleeves × n ticker→sleeve mapping matrix (one 1 per row, the rest 0 — see the ticker proxy table in section 7); τ is the workbook's Policy Target (no single stock) column; Ω is the workbook's sleeve covariance matrix. λ = TURNOVER_LAMBDA = 0.01, the same constant as the FF5/CVaR optimizer's TE-objective turnover penalty. The |x_i − x0_i| and max(x0_j − x_j, 0) terms are passed to SLSQP directly (this path does not introduce explicit slack variables the way 10.2 does — they're evaluated inside the objective/constraint functions each iteration) and solved with the same method="SLSQP", ftol=1e-12, maxiter=2000 settings.

taxRate_j,budget is taxRate_j with MSTR's rate zeroed out — the same exclude_from_tax_budget device Path C/D use in 10.2: MSTR's sale is free from the 2% budget constraint's point of view (a separate taxable strategy is assumed to absorb MSTR's own tax), while the trade table it feeds still reports MSTR's true tax cost, computed from the unmodified taxRate_j, for full transparency. SAA_TAX_BUDGET and the 50% MSTR sale cap are both defined locally in optimize_saa_mvo.py, independent of Path C/D's TAX_BUDGET (2%, defined in optimize_tax_cvar_mvo.py) and their sale caps (70%/30%) — the tax-budget percentage happens to match Path C/D's, but it is tracked as a separate constant, not a shared one, and the 50% MSTR cap is unique to this path. NO_ADD_TICKERS, by contrast, is shared — optimize_saa_mvo.py imports it directly from optimize_tax_cvar_mvo.py rather than redefining it, so SHV's no-buy rule is a single setting that applies identically to Path C, Path D, and Path SAA, not three separately-maintained copies.

11. Optimization configurations

Section 10 gave the general QP form each script solves. Exactly three trade-proposal paths are computed now — no "Joint" solve, no Path A, no Path B — each rendered as its own card/tab in rebalance_dashboard.html: Path C and Path D (optimize_tax_cvar_mvo.py, same problem, different MSTR sale cap) and Path SAA (optimize_saa_mvo.py, a fully independent solve). None of the three is CVaR-constrained.

FF5 policy benchmark

construct_benchmark_mvo.py · max-Sharpe over the 5 Fama-French factors, 60–70% market band, 5% non-market floor. One-time, buy-and-hold, never rebalanced. Feeds β_benchmark used by Path C and Path D.

All-equity SAA target

all_equity_saa_covariance.xlsx · no optimization — the Policy Target (no single stock) column is read directly as τ. Single Stock fixed at 0%. Feeds the SAA path's own objective (its weights are still evaluated against the FF5 benchmark afterward, purely for risk-attribution reporting — see 11.3).

12. Risk attribution and interpretation

portfolio_risk_attribution.py separates two kinds of risk:

ComponentHow it is calculatedWhat it tells you
Factor TE contributionEuler allocation of sqrt(Δβ'ΣΔβ) by factor.Which active style bets create systematic tracking risk.
Idiosyncratic TE contributionWeighted residual variances from each ticker regression, assuming cross-ticker residual covariance is zero.How much risk is not represented by FF5 factors, often concentrated single-stock risk.
Tail CVaR contributionAverage factor returns only over the portfolio's worst 5% annual scenarios.Which factors mattered specifically in bad active-return windows.
Exposure z-scoreStandardize each ticker's beta relative to the household's own ticker universe.Relative tilt within this book, not a market-wide Barra score.

13. What is real, synthetic, and unfinished?

Research outputs

FRED, Ken French, and Yahoo Finance inputs are external data. The committed factor-research CSVs are historical research outputs, not automatically refreshed live estimates.

Sample portfolio

The sample holdings and its reported portfolio results are fabricated demonstration data. They validate the mechanics, not a real person's performance.

Real-household track

The workbook-driven optimizer is designed for actual account data, but its results remain model-based proposals and depend on price history, gain aggregation, tax assumptions, and constraints.

Prototype track

benchmark_tracking_error_model.py deliberately generates a synthetic portfolio with style drift. Its rolling-beta and Ledoit–Wolf outputs are machinery demonstrations, not household results.

14. Main limitations to keep in mind

  • Macro factors are PCA scores of indicators, not directly tradable factor returns.
  • Forward-filling can preserve stale observations and may understate the timing uncertainty of slow data.
  • Most estimates are in-sample; there is no complete walk-forward validation or out-of-sample forecast test.
  • OLS betas are static in the primary pipeline. The time-varying-beta sampler is standalone and not wired into the production flow.
  • Factor-only TE can materially understate risk for concentrated positions with large regression residuals.
  • The optimizer uses aggregated ST/LT gains rather than tax-lot dates, so actual realized tax outcomes can differ.
  • Overlapping annual CVaR windows are dependent observations, and the arithmetic 12-month return approximation is chosen to preserve linearity.
  • Some factor-research scripts contain hardcoded Windows paths; rebuilds on another machine require path edits.

15. Practical run order

  1. Build the factor panel with fetch_macro_fred.py, pull_yfinance_data.py, and transform_data_ff.py.
  2. Run quant_model_macro_1.py for macro PCA, then quant_model_macro_2.py for VARX.
  3. Run quant_model_macro_3.py and quant_model_macro_4.py for asset betas and inference.
  4. Run vif_check.py and regenerate charts when diagnostics or upstream data change.
  5. For the sample track, generate holdings, fetch prices, construct the benchmark, and calculate exposures.
  6. For the real track, ingest the workbook, fetch real holding prices, construct the FF5 benchmark, run the tax-constrained optimizer (Paths C/D), run the SAA optimizer from all_equity_saa_covariance.xlsx, attribute FF5 risk (including Path SAA), and generate the dashboard.
